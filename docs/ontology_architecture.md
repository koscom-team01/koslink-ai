# kosLINK AI: 3-Layer 반도체 밸류체인 온톨로지 아키텍처 명세서

본 문서는 **kosLINK AI** 인덱스 빌더 시스템의 핵심 기반인 Neo4j 그래프 데이터베이스 온톨로지 구성 사양과 데이터 수집 및 업데이트 파이프라인의 구조를 설명합니다.

---

## 1. 온톨로지 스키마 설계 (Ontology Schema)

온톨로지는 거시적 투자 트렌드부터 미시적 종목 수준까지 유기적으로 매핑되도록 **3-Layer 계층형 그래프 스키마**로 구성됩니다.

```
  [Layer 1: Theme (테마)]
          ▲
          │ (BELONGS_TO)
  [Layer 2: Role (기술 역할군)]
          ▲
          │ (BELONGS_TO)
  [Layer 3: Stock (상장사 종목)] ──(SUPPLY_TO)──► [Stock (수요 기업)]
```

### 1) 노드 스키마 (Node Schema)

#### ① Theme (테마 노드)
금융 시장을 주도하는 메가 트렌드 카테고리입니다. (예: 온디바이스 AI, HBM, CXL)
*   `id`: 고유 식별자 (예: `T_HBM`)
*   `label`: 테마 명칭 (예: `HBM`)
*   `description`: 테마 기술 설명

#### ② Role (공정 기술 역할 노드)
반도체 제작 공정상 핵심 기술 분류군입니다. (예: 디자인하우스, 패키징 장비, EUV 등 10대 역할)
*   `id`: 고유 식별자 (예: `R_PKG_EQUIP`)
*   `label`: 역할군 명칭 (예: `패키징 장비`)
*   `description`: 역할군의 공정상 정의 및 위상

#### ③ Stock (주식 종목 노드)
국내외 반도체 공급망에 참여하는 개별 기업 노드입니다.
*   `id`: 고유 ID (예: `S_005930`)
*   `name`: 기업 한글 공식 명칭 (예: `삼성전자`)
*   `ticker`: 6자리 상장 종목코드 (비상장사인 경우 생략 혹은 별도 식별자)
*   `marketCap`: 오늘의 실시간 시가총액 수치 (원화 기준)
*   `capSize`: 시총 규모에 따른 대/중/소 체급 분류 (`Large`, `Mid`, `Small`)
*   `marketType`: 상장 시장구분 (`KOSPI`, `KOSDAQ`, `UNLISTED`)
*   `sourceAPI`: 데이터 수집 원천 API 명칭
*   `lastUpdated`: 데이터 최신화 타임스탬프

---

### 2) 관계선 스키마 (Edge Schema)

#### ① BELONGS_TO (소속 관계)
*   `Stock ➔ Role` 또는 `Role ➔ Theme` 방향으로만 연결됩니다.
*   *예: (리노공업) -[:BELONGS_TO]-> (테스트 부품)*

#### ② SUPPLY_TO (공급/거래 관계)
*   `Stock ➔ Stock` (공급사 ➔ 수요처) 방향으로 연결되는 핵심 트랜잭션 관계선입니다.
*   `product`: 공급 및 계약 제품/서비스 명칭 (예: `TC본더`)
*   `amount`: 계약 금액 (원화 기준 포맷팅 문자열)
*   `fact_source`: 관계를 입증하는 DART 공시 보고서 제목
*   `dartUrl`: 금감원 공시 상세 웹 뷰어 URL (감사용 링크)
*   `confidenceScore`: 정보의 신뢰도 수치 (DART 공시 기반인 경우 `0.98~0.99`)
*   `extractionMethod`: 수집 및 파싱 기법 (`OpenAI_Structured_Cron_Parser` 등)
*   `status`: 준법 감시용 검증 상태 (`VERIFIED`, `SPECULATIVE`)
*   `verifiedBy`: 수집 주체 에이전트 명칭
*   `verifiedAt`: 검증 완료 시간 타임스탬프

## 2. 사용 데이터 소스 및 API (Data Sources & APIs)

파이프라인은 세 가지 외부 데이터 피드와 AI 엔진을 융합하여 운영됩니다.

| 데이터 소스 | 제공 정보 | 인증 형태 | 용도 |
| :--- | :--- | :--- | :--- |
| **금융감독원 Open DART** | 1) 공시 목록 검색 (`list.json`) <br> 2) 원본 보고서 ZIP 다운로드 (`document.xml`) | DART 개인 API Key 발급 필요 | 초기 데이터 구축 시 기업의 원본 **사업보고서** 텍스트 확보 |
| **금융감독원 공개 RSS 피드** | 당일 실시간 접수 공시 헤드라인 및 요약문 | **Keyless (완전 공개)** | 실시간 공급망 변동 공시(단일판매공급계약) 감지 |
| **네이버 금융 (HTML)** | 1) 기업명 기반 종목코드 검색<br> 2) 종목별 실시간 시가총액 | **Keyless (완전 공개)** | 1) 신규 종목코드 검색<br> 2) 시총 및 대/중/소 체급 매일 동기화 |
| **OpenAI API** | `gpt-4o-mini` 활용 비정형 텍스트 구조화 | OpenAI 개인 API Key 발급 필요 | 원본 보고서 줄글에서 거래처 및 계약 팩트 추출 |

## 3. 초기 데이터 구축 프로세스 (Bootstrapping Workflow)

아무것도 없는 데이터베이스에 3-Layer 온톨로지의 기본 뼈대를 수립하는 절차입니다.

```
[1단계: 마스터 스키마 선언]
  - Neo4j 연결 및 Theme, Role, Stock 노드 식별자 고유성(Uniqueness) 제약 조건 설정

[2단계: 테마 및 기술 분류 정의 적재]
  - 3대 핵심 테마(HBM, On-Device AI, CXL) 및 10대 역할 노드를 생성하고 BELONGS_TO로 연동

[3단계: DART 사업보고서 원본 다운로드]
  - 53개사 Ticker 정보를 바탕으로 Open DART API 'list.json'을 호출하여 가장 최근 '사업보고서'의 rcept_no 추출
  - DART 'document.xml'을 통해 원본 보고서 HTML 패키지(ZIP) 다운로드

[4단계: 사업의 개요 추출 및 LLM 분석]
  - 다운로드한 ZIP 파일 내에서 '사업의 개요' 혹은 가장 용량이 큰 본문 HTML 파일 검출
  - HTML 태그를 정제하고, 순수 텍스트 본문(약 2만 자)을 추출하여 OpenAI gpt-4o-mini 모델로 주입
  - AI가 본문을 읽어 해당 기업의 제품군을 분석하고, 거래 대상 기업과 매출 비중 팩트를 정형 JSON으로 반환

[5단계: 기초 온톨로지 적재 완료]
  - 추출된 정보를 파싱하여 Stock 노드를 생성하고 Role 노드에 연결
  - 입증된 거래 파트너 사이에 SUPPLY_TO 관계선을 생성하고 감사용 공시 주소를 엣지 속성으로 기록
```

## 4. 실시간 업데이트 프로세스 (Real-time Pipeline Update)

쿠버네티스 크론잡(CronJob)에 의해 주기적으로 구동되어 살아있는 온톨로지를 유지하는 배치 연산입니다.

```
[1단계: 등록 종목 시가총액 동기화]
  - Neo4j 데이터베이스에 등록된 모든 Stock 노드들로부터 Ticker 리스트를 동적으로 읽어옴
  - 네이버 금융을 크롤링하여 오늘자 실시간 시가총액 수치 획득 후 대/중/소 체급 재연산
  - 변경된 시가총액과 최신 타임스탬프를 Neo4j에 UPDATE

[2단계: 실시간 공시 스트림 스캔]
  - 금감원 DART RSS 공개 피드를 호출하여 오늘 등록된 모든 공시 헤드라인 획득
  - 제목 중 '단일판매ㆍ공급계약체결' 문구가 들어간 항목만 1차 필터링

[3단계: 신규 계약 정형 분석 (OpenAI)]
  - 필터링된 공시 본문 요약 데이터를 OpenAI API에 전송하여 공급처, 수요처, 제품명, 계약금액 추출

[4단계: 동적 온보딩 및 공급망 반영]
  - 획득한 기업명으로 네이버 금융을 실시간 검색하여 6자리 종목코드 획득
  - 해당 종목이 기존 DB에 없던 신규 기업인 경우, Stock 노드를 신규 생성하고 기본 역할군에 자동 소속시킴
  - 공급사와 수요처 노드 간에 SUPPLY_TO 관계선을 연결하고 공시 일련번호 및 감사 메타데이터 주입
```

## 5. 데이터 정합성 보장 가드레일 (Data Quality & Integrity)

LLM의 환각(Hallucination) 및 중복 엣지 생성을 원천 방어하기 위해 설계된 정제 룰입니다.

1.  **역할군 폐쇄 루프 제약**: LLM은 관계를 추출할 때 오직 정해진 10대 역할군 ID(`R_CHIP`, `R_IP` 등)만을 할당할 수 있도록 구조화 JSON 스키마 제약을 적용받습니다.
2.  **공시 접수번호 기반 중복 제거 (Idempotency)**: 동일한 거래선에 대해 매일 수집기가 돌더라도, 관계선에 공시 접수번호(`receiptNo` 혹은 `dartUrl`)를 유니크 키로 사용하여 `MERGE` 쿼리를 실행하므로 중복 연결선 생성이 차단됩니다.
3.  **상장 여부 대응 예외 처리**: 수요처(바이어)가 비상장사나 해외 기업(예: TSMC 등)으로 확인되어 종목코드가 검출되지 않을 시, 시스템 오류로 죽지 않고 `S_UNLISTED_회사명` 형태로 정규화된 비상장용 노드를 안전하게 자동 온보딩합니다.
